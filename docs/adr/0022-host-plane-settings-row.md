# The settings namespace is Host-plane; the delegation surface stays agent-plane

- Status: Accepted
- Date: 2026-08-21

ADR 0021 made the Host settings service a configuration source for the one `Config` schema Legion already had. It left one question unasked: *which composed row registers the namespace*. Legion answered it by accident — whichever row ran — and the answer was wrong, because a namespace and a Profile catalog have different lifetimes.

A DSH settings registration is an effect on the registering fiber: disposing that fiber removes the namespace and its observers. An Agent Preset subtree is owned by the agent that mounted it. Compose those two facts and the `legion` namespace is served exactly while a session using the Legion preset is alive — the configuration surface offers the card mid-session, drops it when the last such session ends, and shows nothing at all after a restart, while values the user already saved stay in the user document with no way left to edit them. The Web half fails the same way for a different reason: the client module registry composes its table from the Host loader entries, and a preset subtree is plugged directly rather than created as a loader entry, so a package mounted only inside a preset is never discovered and its card bundle is never served to the page.

So Legion ships a Host-plane row, and the bundle patch stops being empty. What that row may contribute is the whole design question, because `tools` and `system-prompt` are layered registries: a Host row lands in the global layer and hands every agent in the process a delegation surface it never asked for. That is precisely what Legion is not. The row therefore declares `role: settings` and contributes the namespace and nothing else — no tool, no prompt section, no projection, no service.

The role is a composition fact read from the row entry, never from the settings layer. The temptation to resolve it like every other field is exactly the failure to avoid: a stored section that could flip a row to `settings` would withdraw every delegation surface in the deployment from inside the document the surface exists to edit. `materializeConfig` does not carry the role into its output either, so nothing downstream can rediscover it through a resolved value.

The row that owns the namespace cannot also be the row that reads it, so the consuming half is now explicit. A delegation row beside a served namespace reads the raw stored section and layers it over its own entry — schema defaults, then this row entry, then the user overrides — which is the same order the Host would have applied had this row registered. Reading the owner resolved value instead would answer with another row composition entry underneath, and the preset that names the Profiles would lose to a Host row that names none. Which half runs is decided by what the Host already serves rather than by configuration, so a duplicate registration, which the Host refuses loudly, is impossible however many Legion rows a deployment composes. Two concurrent sessions now both get live reconfiguration; before this ADR the second one silently lost it to that refusal.

Layering locally means reproducing one Host walk: plain objects merge recursively, everything else replaces. The provider keeps that walk private, so there is nothing to reuse and a faithful copy is what makes a consuming row resolve what the owning row would have. It is pinned by a test that proves the merge is recursive rather than wholesale.

Validation splits along the same seam. A namespace is process-wide while a catalog belongs to one row, so the owner judges only what holds for any catalog — a blank tool name, an inverted durable policy, an unusable resource root — and a `defaultProfile` naming a Profile one row defines and another does not is left to each delegation row, which already keeps its last publishable generation and logs when a stored section cannot be materialized. Refusing such a write on behalf of one catalog would refuse it for every other.

The cost is one field in a public schema and one more row in a composition a user can read. The alternative shapes were worse. A settings-only subpath entry point (`dsh-legion/settings`) mounts cleanly but is invisible to the client module registry, which resolves `<row name>/package.json` and expects the served bundle to register under the row id, so the card would stay missing — the second half of the bug. Detecting the plane structurally, by the absence of an agent scope, would silently change what an existing Host row means and take away a deployment ability to mount Legion globally on purpose. Leaving the namespace unregistered on the Host plane and letting preset rows fight over it is what this ADR replaces.
