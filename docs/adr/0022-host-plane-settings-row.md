# The settings namespace is Host-plane; the delegation surface stays agent-plane

> **Terminology: ADR 0022.** The retired Legion nouns `Profile` and `Team` became Specialist and Cohort; retired machine spellings remain only where compatibility history requires them.

- Status: Accepted
- Date: 2026-08-21

ADR 0021 made the Host settings service a configuration source for the one `Config` schema Legion already had. It left one question unasked: *which composed row registers the namespace*. Legion answered it by accident — whichever row ran — and the answer was wrong, because a namespace and a Specialist catalog have different lifetimes.

A DSH settings registration is an effect on the registering fiber: disposing that fiber removes the namespace and its observers. An Agent Preset subtree is owned by the agent that mounted it. Compose those two facts and the `legion` namespace is served exactly while a session using the Legion preset is alive — the configuration surface offers the card mid-session, drops it when the last such session ends, and shows nothing at all after a restart, while values the user already saved stay in the user document with no way left to edit them. The Web half fails the same way for a different reason: the client module registry composes its table from the Host loader entries, and a preset subtree is plugged directly rather than created as a loader entry, so a package mounted only inside a preset is never discovered and its card bundle is never served to the page.

So Legion ships a Host-plane row, and the bundle patch stops being empty. What that row may contribute is the whole design question, because `tools` and `system-prompt` are layered registries: a Host row lands in the global layer and hands every agent in the process a delegation surface it never asked for. That is precisely what Legion is not. The row therefore declares `role: settings` and contributes the namespace and nothing else — no tool, no prompt section, no projection, no service. The services Legion depends on follow that same line: `agents`, `tools`, `subagents`, and `systemPrompt` are no longer a package-level `inject` but `DELEGATION_INJECT` on an inner plugin that `apply` mounts only for a row that is not a settings row, so the Host-plane row waits for none of them. Declared on the package they would have applied to every row regardless of its role, and a headless composition serving settings without one of the four would leave the settings row pending forever with a missing card as its only symptom. `inject` accordingly left the public export list and `DELEGATION_INJECT` joined it.

The role is a composition fact read from the row entry, never from the settings layer. The temptation to resolve it like every other field is exactly the failure to avoid: a stored section that could flip a row to `settings` would withdraw every delegation surface in the deployment from inside the document the surface exists to edit. `materializeConfig` does not carry the role into its output either, so nothing downstream can rediscover it through a resolved value.

The row that owns the namespace cannot also be the row that reads it, so the consuming half is now explicit. A delegation row beside a served namespace reads the raw stored section and layers it over its own entry — schema defaults, then this row entry, then the user overrides — which is the same order the Host would have applied had this row registered. Reading the owner resolved value instead would answer with another row composition entry underneath, and the preset that names the Specialists would lose to a Host row that names none. Which half runs is decided by what the Host already serves rather than by configuration. What that guarantees is narrower than never colliding: no row registers a namespace it saw as served, a row that loses the race between that check and its own `register` falls back to consuming what the winner now serves rather than to its bare entry, so it keeps live reconfiguration either way, and the settings row's own duplicate refusal — reachable when a delegation row got there first — is caught and logged rather than taking the row down. Two concurrent sessions now both get live reconfiguration; before this ADR the second one silently lost it to that refusal. One limitation stays: if the settings row's own fiber is disposed while delegation rows are consuming, the namespace stops being served and no surviving row takes it over until the next mount, so those consumers degrade to their composition entries.

Layering locally means reproducing one Host walk: plain objects merge recursively, everything else replaces. The provider keeps that walk private, so there is nothing to reuse and reproducing it is what makes a consuming row resolve what the owning row would have. The copy is exact but for one deliberate hardening: Legion skips an own `__proto__` key, which the Host walk does not, so a stored document carrying one resolves to an ordinary object here instead of to an object whose prototype the document supplied. `Config` declares no such field and unknown-key validation would reject it anyway, so the divergence costs nothing a deployment can observe and removes a shape no configuration should be able to take. It is pinned by a test that proves the merge is recursive rather than wholesale.

Validation splits along the same seam. A namespace is process-wide while a catalog belongs to one row, so the owner judges only what holds for any catalog — a blank tool name, an inverted durable policy, an unusable resource root — and a `defaultProfile` naming a Specialist one row defines and another does not is left to each delegation row, which already keeps its last publishable generation and logs when a stored section cannot be materialized. Refusing such a write on behalf of one catalog would refuse it for every other.

The cost is one field in a public schema and one more row in a composition a user can read. The alternative shapes were worse. A settings-only subpath entry point (`dsh-legion/settings`) mounts cleanly but is invisible to the client module registry, which resolves `<row name>/package.json` and expects the served bundle to register under the row id, so the card would stay missing — the second half of the bug. Detecting the plane structurally, by the absence of an agent scope, would silently change what an existing Host row means and take away a deployment ability to mount Legion globally on purpose. Leaving the namespace unregistered on the Host plane and letting preset rows fight over it is what this ADR replaces.
